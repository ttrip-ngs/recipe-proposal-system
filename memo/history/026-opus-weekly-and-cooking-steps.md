# 026 週間提案を Opus 5.5 に切り替え、作り方 (steps) を追加

2026-09-26

## 背景

023 で週間提案は 32.5 秒 / 16.8 円まで下がったが、ユーザーから「不味い献立はつらい、
Opus 5.5 と比べたい」「簡単な手順も欲しい」「プルコギなどを Haiku に作らせるのは心配」
との要望があった。コストより献立の質を優先する判断。

## 比較と判断

### 骨子 (何を作るか)

同じプロンプト・同じ候補レシピで各 3 回生成した (構造化出力あり)。

| モデル / effort | 時間 | 出力トークン | 1 回のコスト |
|---|---|---|---|
| Sonnet 5 / low | 15 秒 | 約 1,470 | 約 5.2 円 |
| Opus 5.5 / low | 15 秒 | 約 1,500 | 約 7.1 円 |
| Opus 5.5 / medium | 32-38 秒 | 約 3,100-3,500 (thinking 込み) | 約 12.5 円 |

- Sonnet 5 / low は 3 回中 2 回、7 日とも副菜「ほうれん草のおひたし」・汁物「豆腐とわかめの
  味噌汁」の繰り返しになった。「卵不使用コーンスープ」のような不自然な料理名も出た
- Opus 5.5 / low は和洋中エスニック・秋の旬食材まで散らばり、十分な質
- Opus 5.5 / medium が最も良く、夫の好物 (牛肉のプルコギ)、週末の手作り餃子、マヨネーズや
  卵入りスープの回避まで 3 回とも安定していた → **骨子は Opus 5.5 / medium**

注意: この比較時、エミュレータの recipes に統合テストのレシピ (「E2E 牛丼」「統合テスト肉じゃが」)
が 33 件混入していた (後述)。両モデルとも同じ入力なので比較は成立しているが、Sonnet の崩れは
この汚れた候補をそのまま拾ったことも一因。

### 詳細 (食材リスト)

Opus 5.5 / medium の骨子を固定し、食材リストを 3 モデルで生成して比べた。

| モデル | 週あたり | 気になった点 |
|---|---|---|
| Haiku 4.5 | 約 5.8 円 | 餃子が「豚肉 300g」(ひき肉でない) でニラ・片栗粉なし、麻婆豆腐の豆板醤が大さじ 2 |
| Sonnet 5 / low | 約 12 円 | ミネストローネに「セロリ 0 本」(夫の嫌い食材・分量も不正) |
| Opus 5.5 / low | 約 17.5 円 | ほぼ問題なし。「固形コンソメ (卵・甲殻類不使用)」まで配慮 |

→ **詳細も Opus 5.5 / low**。`resolve_detail_model` のプロバイダ別テーブル (anthropic → Haiku) は
撤去し、既定では骨子と同じモデルを使う (`LLM_DETAIL_MODEL` での上書きは残す)。

## 実装

### 1. モデルと effort

- `AnthropicDirectClient.DEFAULT_MODEL` を `claude-opus-5-5` に変更
- effort をモデル別 (023 の `_EFFORT_BY_MODEL`) から用途別 (`factory._EFFORT_BY_PURPOSE`) に変更。
  同じ Opus 5.5 でも骨子 medium / 詳細 low と使い分けるため。クライアントはコンストラクタで
  effort を受け取り、Haiku 4.5 (effort を送るとエラー) は日付付き ID を含めて送らない
- 評価ランナーも `effort_for(purpose)` で本番と同じ effort を使う
- `pricing.py` に Opus 5.5 (4 / 20 USD, cache read 0.20, cache write 5.0) を追加
- max_tokens は thinking を含むため、骨子 6000 → 12000、詳細 2000 → 4000 (手順の分) に拡大

### 2. 旧方式 (1 回で 7 日分) の削除

021 の撤去基準 (実測コストが現行を下回る) を 023 で満たしたため、ユーザー判断で削除した。
`suggest_weekly_dinner_*.yaml`、`_generate_single_call` / `_single_attempt`、
`WEEKLY_SPLIT_ENABLED`、`LLMWeeklyProposal` / `LLMWeeklyDay`、フェイクの週間応答を削除し、
`plan_week` の `detail_llm` を必須にした。旧方式向けの週間テスト 13 件は、`output_schema` で
骨子 / 詳細を判別する共通フェイクに置き換え、テストの意図 (単日修復、メタ集計、パース再試行など)
は維持した。旧方式専用の 2 件のみ削除。

### 3. 作り方 (steps)

- `LLMDish` / `LLMDishIngredients` に `steps` (必須, 1-6 件) を追加。単日提案にも付ける
  (単日修復の結果も週間の画面に並ぶため)
- プロンプト: `detail_day_ingredients_system` v2 / `_user` v2、`suggest_dinner_system` v2。
  「3-5 ステップ、1 ステップ 40 字以内」「手順に出す食材は ingredients と同じ表記のものだけ」
  「〜不使用 / 〜抜き / アレルギー の注記を書かない」を指示
- 食材と手順は**同じ呼出**で生成する (別呼出にすると手順にだけ別の食材が出うる)
- 保存: `NormalizedDish.steps` → `proposals` (dishes / days[].dishes) と `MealPlanDish.steps`。
  旧ドキュメントは steps なしで読める (既定値 `()`)。backfill は
  `scripts/migrate_add_dish_steps.py` (dry-run 既定。エミュレータで 14 + 25 件適用し冪等を確認)
- 画面: 材料と作り方の表示を `partials/_macros.html` の `dish_details` に共通化し、
  日別詳細・週レビュー・提案結果の 3 箇所の重複を解消。作り方は `<details>` の番号付きリスト

### 4. 手順のアレルゲン検査 (ガードレール)

手順は自由文で、食材リストのような完全一致では検査できない。「手順にも食材リスト以外を書くな」
の指示だけでは保証にならないため、`validate_recipe` が `recipe.steps` の文章をアレルゲンの語で
部分一致検査し、ヒットしたら `block` にする。

- 検査語はメンバーのアレルギーに関係する canonical と全エイリアスだけ
  (`NormalizerDictionary.text_terms_for`)。家族に関係の無い語での誤検出を避ける
- 短い語の誤検出は `aliases.yaml` の `text_match_exclude` (辞書 version 3) で外す。
  実測 (Opus 5.5 の手順 279 件を全アレルゲングループで照合) で誤検出した
  パン (フライパン)・とり (冷水にとり)・牛 (牛乳)・もも (鶏もも肉) と、同種の モモ・乳・いか・
  かに (なめらかに)・さけ (避ける) を登録。除外は語単位で、パン粉などの別表記は検出する
- サンプル家族 (卵・落花生・甲殻類) の語での誤検出は 279 件中 0 件だったため、`warn` ではなく
  `block` にした (ヒット時は既存の単日修復に回る)

## 検証結果

- `uv run pytest`: 全件パス (ガードレール 12 件、週間の手順テスト 2 件、保存往復など追加)
- `uv run ruff check` / `uv run ruff format` / `uv run mypy src`: クリーン
- ゴールデンセット評価: Fake 11 件中 10 件 (G101 は既知)、`--live` (Opus 5.5) で **11 件中 11 件**
- 検証環境のアプリ経由で週間提案 1 回: **48.7 秒 / 51.4 円**、7 日すべて確定、単日修復 0 回、
  週レビュー画面に 21 品すべての作り方が表示されることを確認
  (内訳: 骨子 13.5 円 / 34 秒、詳細 7 並列で約 38 円 / 最大 13 秒)

## 未検証 / 残課題

- **コストが 023 の約 3 倍** (16.8 → 51.4 円/週、月 200 円程度)。ユーザーの質優先の判断による。
  詳細フェーズは 7 並列のため Prompt Caching の書き込み (1.25 倍) が各呼出で発生しており、
  キャッシュ読み込みは効いていない。詳細の `cache_control` を外すと 1 回あたり約 0.4 円下がる見込み
  (probe の 24 円見積もりはキャッシュ書き込みを計上しておらず過小だった)
- 手順検査の誤検出は、サンプル家族以外のアレルギー (小麦・乳・大豆など) では実データで未確認。
  `text_match_exclude` は語が増えるたびに人間がレビューする運用 (未知食材の週次レビューと同じ枠)
- **統合テストが開発用エミュレータを汚す**: `tests/integration/conftest.py` が開発と同じ
  プロジェクト `recipe-system-dev` に書き込むため、`uv run pytest` のたびに recipes へ
  「E2E 牛丼」「統合テスト肉じゃが」が増え、事前フィルタの候補に混ざる。本作業では手で削除した。
  テスト用のプロジェクト ID を分けるのが根本対処 (未着手)
- 検証環境の起動は `ENV_FILE=.env.staging` だけでは足りない (Firebase / Firestore SDK は
  os.environ を直接読む) ため `set -a; . ./.env.staging; set +a` が必要で、さらに
  `GOOGLE_CLOUD_PROJECT` をエミュレータの `recipe-system-dev` に合わせる必要がある。
  ドキュメント未反映
