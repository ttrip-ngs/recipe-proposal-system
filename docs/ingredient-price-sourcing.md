# 食材価格(相場)の収集方法 検討

状態: Phase 1 実装済み(基準都市: 福岡市)
作成日: 2026-09-26

## 1. 目的

週単位の予算を踏まえた献立提案を行うため、食材ごとの大体の相場(単価)を取得し、
週の献立の概算費用を決定論的に計算できるようにする。

前提とする計算式:

```
週の概算費用 = Σ (食材の必要量 → 購入単位への換算) × 単価
```

## 2. 結論(推奨)

| 優先 | 収集方法 | 役割 |
|---|---|---|
| 1 | 総務省 小売物価統計調査(動向編)を e-Stat の公開ファイル(Excel)から月次取得 | 相場のベースライン(肉・魚・卵・乳・豆腐・調味料・主要野菜) |
| 2 | 買い物リストのチェック時に実際の支払額を任意入力 | 自家の実勢価格。蓄積後はベースラインより優先 |
| 3 | 農水省 食品価格動向調査(野菜)を週次で参照 | 変動の大きい野菜の週次補正・「今週安い野菜」ヒント |

LLM に価格を推定させる方法は採らない。価格が取れない食材は合計から除外し
「価格不明 N 品目」として明示する(未知食材ポリシー 6.6 と同じ考え方)。

## 4. 最大の課題: 単位換算と品目対応(データ取得より難しい部分)

データの取得自体は容易だが、レシピ側と価格側を結合する部分に実装コストの大半がある。

### 4.1 単位換算

- レシピの食材は `個` `本` `枚` `大さじ` `g` など多様な単位を持つ
  (例: `data/seeds/recipes.example.yaml` の じゃがいも 4個、にんじん 1本、鶏もも肉 2枚、醤油 大さじ3)
- 統計価格は基本銘柄の規格単位(100g、1kg、1パック、1L など)で公表される
- 現行の買い物リスト集約は単位換算を「Phase C スコープ外」としている
  (docs/data-model.md の shopping_lists 節)。予算機能を入れると、この単位換算を
  スコープに戻す必要がある
- 必要な情報: 食材ごとの標準重量(じゃがいも1個 ≒ 150g など)と、調味料の扱い

### 4.2 canonical 名と統計品目の対応

- `aliases.yaml` はアレルゲン判定が主目的で、全食材を網羅していない
- 価格用に `canonical → (統計品目コード, 規格単位, 換算係数)` の対応表が別途必要
- 未対応の食材は合計から除外し、件数を表示する(推測で埋めない)
- ただし name で見つからない場合は canonical(`aliases.yaml` の正規化名)でも照合するため、
  派生品が基本品目の価格で概算される(例: 鮭フレーク → 生鮭、うずら卵 → 鶏卵、和牛 → 牛肉(輸入品))。
  また括弧書きを除去して照合するため「豚肉(バラ)」は「豚肉」の価格になる。目安としては許容し、
  ずれが大きい食材は対応表に name を追加して個別に対応する

### 4.3 調味料・常備品

醤油・砂糖・油など少量を長期間使うものは、1回分の按分コストが小さく誤差も大きい。
初期は予算計算の対象外(常備品扱い)とし、生鮮・主食材に絞るのが現実的。

## 5. 段階的な導入案

### Phase 1: 静的価格表(Firestore 変更なし) — 実装済み

| ファイル | 内容 |
|---|---|
| `src/recipe_system/cost/data/retail_prices.yaml` | 福岡市の食料品価格(銘柄符号 1001〜1999)。自動生成、手で編集しない |
| `src/recipe_system/cost/data/ingredient_price_map.yaml` | 食材名 → 銘柄符号の対応、個数単位の標準重量、常備品リスト。手動管理 |
| `src/recipe_system/cost/estimator.py` | 概算計算 |
| `scripts/import_retail_prices.py` | e-Stat の公開 Excel から価格表を生成 |

計算の仕様:

- 費用は「使用量 × 規格単価」の按分(パック単位の購入額ではない)
- 単位換算: g/kg、ml/L/cc、大さじ(15ml)/小さじ(5ml)/カップ(200ml)、および対応表の
  `pieces`(例: じゃがいも 1個 = 150g)。重量単価の食材を容量で指定した場合は換算しない
- 食材名は NFKC 正規化・括弧書き除去のうえ name → canonical の順に照合する
- 常備品(調味料・粉・油など)は対象外、対応表に無い食材・分量不明・換算不能は
  「価格不明」として合計から除外し、画面に一覧を出す
- 表示: 週レビュー画面(`/plans/week/{月曜}/review`)に週合計と日別の概算

e-Stat の公開ファイルダウンロードを使うため、アプリケーション ID は不要とした。

#### 月次の更新手順

1. 小売物価統計の新しい月が公表されたら、e-Stat の統計表一覧で対象月の
   「主要品目の都市別小売価格 1001 うるち米 … 2183 学校給食」の statInfId を確認する
2. `uv run python scripts/import_retail_prices.py --stat-inf-id <statInfId>` を実行する
3. `git diff` で価格の変化と品目の増減を確認し、`uv run pytest tests/unit/test_cost_estimator.py`
   (対応表の銘柄符号がすべて価格表にあるかの検査を含む)を通してからコミットする

### Phase 2: 実勢価格の蓄積

- 買い物リストのチェック時に任意で支払額を入力できるようにする
- 同一食材の直近の実勢価格がある場合は統計価格より優先する
- Firestore のフィールド追加となるため、プロジェクト規約 6.4 に従い
  data-model.md の更新と migration スクリプトを同じPRで行う

### Phase 3(必要になったら): 週次の野菜補正

- 農水省 野菜10品目の週次価格を取得し、平年比が低い野菜を
  骨子生成(Sonnet)プロンプトへ「今週安い野菜」として参考情報で渡す

## 6. 献立生成への組み込み方(参考)

- 予算は3レイヤーのうち「強い選好」に置く(アレルゲンのようなハードルールにはしない)
- 予算目標と安い食材ヒントは骨子生成プロンプトに参考情報として渡す
- 費用計算・予算超過判定はコードで決定論的に行う
- 予算超過時の再提案は回数上限を設け、予算の自動緩和は行わない(6.7 と同じ方針)

## 7. 未決事項

- 予算の対象範囲(夕食のみか、朝昼・常備品を含むか)
- 週予算の設定と、献立提案への組み込み(第 6 節)
- 価格不明になる頻出食材の対応表への追加(実際の LLM 出力を見て判断する)
